# 手机与板端故障排查

先核对[版本组合](RELEASES.md)：Android v0.1.5 配板端 v0.1.2。v0.1.0/v0.1.1 不作为当前可用方案。

| 现象 | 已知含义与处理 |
|---|---|
| 未识别到 NFC 墨水屏固件 | 手机读到标签不等于 MCU 协议已运行。核对主板供电、配套固件、上电示例是否完成；复制 READ/Mailbox 诊断 |
| 提示目标邮箱被锁定 | 应用只读检查后停止；不要尝试改锁位或让通用标签写入器解锁 |
| TagLost / transceive failed | 可能是离场、RF/I²C 争用、复位或供电问题，不能单凭文案判断用户移动；保持线圈对准并附完整诊断 |
| 第一条 A204 写失败 | 旧版邮箱落在本板已锁区域；升级 v0.1.2 固件及当前 APK，现邮箱起始页为 90h |
| 100% 后仍在等待 | 100% 表示图片正在提交；收到固件提交 ACK 后出现“等待屏幕刷新”，点“OK，可以拿开手机”即可移开手机。实际刷新仍需约 15 秒 |
| 已发送但未收到刷新确认 | 查看实物是否已刷新；等屏幕停止后重试整图，不在刷新中断电 |
| 取消后屏幕继续闪 | COMMIT 后物理刷新不能撤回；等刷新结束 |
| 覆盖安装失败 | 核对签名证书；自己构建的密钥可能与 Release 不同，见版本说明 |
| 重启后恢复示例图 | 当前仅使用 RAM，没有掉电保存上传图片 |
| 黑字淡、红底白字泛 | 已知物理显示现象；调图像参数不会修改屏幕驱动电压 |

## 收集诊断

失败弹窗 → “复制诊断”。保留：

- 应用版本、手机型号、Android 版本、Tech 列表。
- UID、失败命令、异常类型与 READ/Mailbox 原始字节。
- 固件版本、供电方式、是否接 ST-Link、失败前是否有刷新。
- 是否稳定复现、在哪个阶段失败，以及手机位置是否固定。

诊断只保存在本地并可复制，不自动上传。公开前检查 UID、设备标识等信息。无需 root 或 Shizuku；当前失败日志已经能用于比对身份、锁页和 RF 命令。

## 调试器验证的范围

实板脚本 `tests/hardware_mailbox.py` 通过 SWD 请求 MCU 操作真实 I²C/SRAM，并触发一次刷新。它没有经过手机 RF 接口，不能代替手机实测；也不是只读测试，不要在手机传输时并行执行。

使用匹配 AXF 的符号定位 `g_nfc` 和 `g_status`，不要硬编码其他版本的 RAM 地址。每次编程记录在 `firmware/Runs`。原厂恢复和 EEPROM 比对的边界见[硬件与验证](HARDWARE_AND_VALIDATION.md)。
